  <section class="atif-section not-content">
    <div class="atif-why" data-reveal>
      <h2>Why a shared format?</h2>
      <div class="atif-why__prose">
        <p>Ask three agent frameworks what happened during a run and you get three different answers. One keeps a chat transcript. Another writes a list of unlabelled items. A third streams fragments you have to stitch back together yourself.</p>
        <p>Each is fine on its own — until you want to compare them. Then every dashboard, eval script, and training job starts with a one-off parser that breaks the next time a framework ships an update. ATIF replaces those parsers with one well-specified file.</p>
      </div>
    </div>
    <div class="atif-audiences">
      <div class="atif-audience" data-reveal>
        <h3>If you build agents</h3>
        <p>Log each event the moment it happens. No buffering whole turns in memory, and no losing the run when a process dies halfway through.</p>
      </div>
      <div class="atif-audience" data-reveal style="--reveal-i:1">
        <h3>If you run evals or RL</h3>
        <p>Compare runs across frameworks and models on equal footing: the same steps, the same action names, the same token and cost fields.</p>
      </div>
      <div class="atif-audience" data-reveal style="--reveal-i:2">
        <h3>If you debug trajectories</h3>
        <p>See what actually happened, in order — including the retries, rewinds, and subagents that most logs quietly throw away.</p>
      </div>
    </div>
  </section>

  <section class="atif-section not-content">
    <div class="atif-section__head" data-reveal>
      <h2>From a live stream to a tidy record</h2>
      <p>ATIF has two modes that share one line-by-line JSON format. You write the first while the agent runs. The second is what you read afterwards.</p>
    </div>
    <div class="atif-flow" data-reveal>
      <div class="atif-flow__step">
        <p class="atif-flow__tag"><code>.atif-e.jsonl</code></p>
        <h3>Record</h3>
        <p>Your harness appends one small JSON line per event: a prompt arrives, the model replies, a tool returns. Nothing is rewritten, so a crash never corrupts what is already on disk.</p>
      </div>
      <div class="atif-flow__step">
        <p class="atif-flow__tag"><code>events → trajectories</code></p>
        <h3>Consolidate</h3>
        <p>A deterministic pass folds those events into numbered steps, attaches each tool result to the call that made it, and files retries, forks, and subagents as linked sibling trajectories.</p>
      </div>
      <div class="atif-flow__step">
        <p class="atif-flow__tag"><code>.atif.jsonl</code></p>
        <h3>Query</h3>
        <p>The result reads top to bottom like a story, and maps one-to-one onto Protobuf and six warehouse tables — so the same run works in a notebook, a viewer, or BigQuery.</p>
      </div>
    </div>
  </section>

  <section class="atif-section not-content">
    <div class="atif-section__head" data-reveal>
      <h2>What you get out of it</h2>
      <p>Four things that are tedious to build yourself, and that every team working with agents ends up needing.</p>
    </div>
    <div class="atif-features">
      <div class="atif-feature" data-reveal>
        <FeatureGlyph kind="canonical" />
        <h3>One name for the same action</h3>
        <p>Claude Code calls it <code>Bash</code>. Codex calls it <code>exec_command</code>. Cursor calls it <code>run_terminal_cmd</code>. ATIF keeps the original call and adds a typed <code>shell_command</code> overlay — one of 28 canonical action kinds — so a single query covers every harness.</p>
        <a href="/spec/v2.0/references/canonical-actions/">Canonical actions catalog</a>
      </div>
      <div class="atif-feature" data-reveal style="--reveal-i:1">
        <FeatureGlyph kind="multimodal" />
        <h3>Steps that keep everything in order</h3>
        <p>A step holds reasoning, text, images, audio, and tool calls in the order they happened, with each action's arguments, output, timing, and approval right beside it. Oversized outputs keep a readable preview and a pointer to the full blob.</p>
        <a href="/spec/v2.0/#steps-multimodal-content--context-compaction">Steps and multimodal content</a>
      </div>
      <div class="atif-feature" data-reveal>
        <FeatureGlyph kind="lineage" />
        <h3>Nothing gets thrown away</h3>
        <p>Retries, rewinds, forks, best-of-N candidates, and subagents are stored as sibling trajectories that point back to where they branched. Replay the path the agent kept — or study the ones it abandoned.</p>
        <a href="/spec/v2.0/#ndjson-records-sessions-trajectories--lineage">Lineage and branching</a>
      </div>
      <div class="atif-feature" data-reveal style="--reveal-i:1">
        <FeatureGlyph kind="warehouse" />
        <h3>Ask questions in SQL</h3>
        <p>Schemas ship as JSON Schema, Protobuf, and warehouse DDL that stay in lockstep. Load runs into BigQuery or DuckDB and ask which model fails the most shell commands, without touching raw JSON.</p>
        <a href="/spec/v2.0/references/projections/">Wire and warehouse projections</a>
      </div>

    <div class="atif-section__head not-content" data-reveal>
      <h2>One moment, three views</h2>
      <p>A user asks an agent to run the auth tests. Here is that single moment as it is streamed, as it is stored, and as it is queried.</p>
    </div>

<Tabs>
<TabItem label="As it happens">

While the agent works, the harness appends one line per event. These three share a `response_id`, which is how ATIF knows they belong to the same model turn.

```jsonc title="session.atif-e.jsonl"
// 18:00:02 — the model starts thinking
{ "event_id": "ev-2", "response_id": "msg_01",
  "step": { "source": "agent", "content": [{ "reasoning": { "text": "I'll run pytest on test_auth.py." } }] } }

// 18:00:03 — and asks to run a command
{ "event_id": "ev-3", "response_id": "msg_01",
  "step": { "source": "agent", "actions": [{ "action_id": "toolu_01", "name": "Bash", "arguments": { "command": "pytest test_auth.py" } }] } }

// 18:00:04 — the command finishes
{ "event_id": "ev-4",
  "action": { "action_id": "toolu_01", "output": [{ "text": "1 passed in 0.12s" }] } }
```

</TabItem>
<TabItem label="Once it's stored">

Consolidation folds those three events into one step. The tool result now sits inside the call that produced it, next to a canonical description any harness would recognise.

```jsonc title="session.atif.jsonl"
{
  "type": "step",
  "trajectory_id": "traj-1",
  "step": {
    "step_id": 2,
    "source": "agent",
    "event_ids": ["ev-2", "ev-3"],                // where this step came from
    "content": [
      { "type": "reasoning", "reasoning": { "text": "I'll run pytest on test_auth.py." } },
      { "type": "text", "text": "Running pytest now." },
      { "type": "action", "action_id": "toolu_01" }
    ],
    "actions": [
      {
        "action_id": "toolu_01",
        "name": "Bash",                            // what the harness called it
        "arguments": { "command": "pytest test_auth.py" },
        "output": [{ "type": "text", "text": "1 passed in 0.12s" }],
        "canonical": {                             // what it means everywhere
          "type": "shell_command",
          "shell_command": { "cwd": "/workspace", "command": "pytest test_auth.py", "exit_code": 0 }
        }
      }
    ],
    "metrics": { "input_tokens": 1200, "output_tokens": 45, "cache_read_tokens": 1000 }
  }
}
```

</TabItem>
<TabItem label="When you query it">

Load the same file into a warehouse and the canonical overlay becomes a column. This query works whether the run came from Claude Code, Codex, Cursor, or your own loop.

```sql title="shell-failures.sql"
-- Which agents fail the most shell commands?
SELECT
  t.agent.name                                        AS agent,
  COUNT(*)                                            AS shell_commands,
  COUNTIF(a.canonical.shell_command.exit_code != 0)   AS failed
FROM actions AS a
JOIN trajectories AS t USING (trajectory_id)
WHERE a.canonical.type = 'shell_command'
GROUP BY agent
ORDER BY failed DESC;
```

</TabItem>
</Tabs>
